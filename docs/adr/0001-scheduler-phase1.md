# ADR-0001: 既存MVPの計算部をTypeScriptの探索エンジンへ分離

- 日付: 2026-11-05
- 状態: 今回のPoC実装で採用。製品要件v1.0の承認ではない。
- 関連: BR-001/004、FR-005〜013/018、HC-001〜008、NFR-007/008/012

## 背景と差分

開始時のmainは文書のみだったが、Draft PR #2にJavaScriptのローカルMVPがあった。
指定リモートブランチはその祖先だったため、既存MVPを継承して改善する。
既存UI・保存・承認・履歴は保持し、新画面は実装しない。

既存の探索は小規模な既知解を扱えたが、solveへの直接入力に対する型・参照・時刻の検証が不十分だった。
探索ノード上限は固定で、時間検査が再帰入口にしかなく、候補を多数棄却するループで遅れる可能性があった。
元の5テストには同種農機2台と打ち切り状態の明示的試験がなかった。

## 決定

- Node.js 22 + TypeScript 5.9.3（開発依存を固定）。実行時はNode標準機能のみ。
- `model.ts`（型）、`validation.ts`（unknown入力検証）、`solve.ts`（探索）、`verify.ts`（独立した結果検査）を分離。
- `strict`、`noUncheckedIndexedAccess`、`exactOptionalPropertyTypes`で型検査。
- `src/core.js`は既存アプリとの互換アダプターを持つ。全アプリの型移行は今回の範囲外。
- 全入力を検証後、先行関係のトポロジカル順で各作業の開始時刻・作業員・農機を列挙する。
- incumbent（現在の最良解）の最終完了時刻以上になる枝を除外するbranch-and-bound。
- 探索と別の制約検査で解を検査し、違反時は例外。入力エラーは`InputError`。
- `solve`は4状態の判別可能なunionを返す。入力/内部エラーは結果に偽装せず例外として既存APIのエラー応答へ渡す。

## 正確性の根拠と制限

列挙順序は作業の実行順序を固定しない。先行関係以外の作業は後で割り当てた作業でも早い時刻を選べる。
有限個の30分スロットと資源の全組合せを列挙し、違反する候補だけを除く。
部分割当の最終完了時刻は以降減らないため、最良値以上の枝を捨てても、それより良い解を失わない。
全探索終了時のみ解ありをOPTIMAL、解なしをINFEASIBLEとする。
停止時は解ありをFEASIBLE、解なしをUNKNOWNとし、最適性・不可能性を主張しない。
同じ最適値の全候補は列挙しない。

N作業、Tスロット、W作業員、M台に対し、候補数の粗い上界は`(T * W * max(1,M))^N`。
区間走査・衝突チェックのコストも乗る。深さ優先探索の割当保持はO(N)、入力は別途必要。
20作業の入力受付は20作業の最適性証明の保証ではない。一般的な大規模計画には不向き。

既定は探索2秒または300,000ノード。`maxNodes`は再帰呼出し数を数え、候補検査数とは異なる。
時計は単調な`performance.now()`。時間チェックを開始時刻・作業員・農機ループにも置く。
同期処理の協調的な打ち切りであり、検証・GC・1回の配列走査までを強制中断する期限ではない。
`elapsedMs`は探索開始から結果検査終了までで、初回の入力検証を含まない。全呼出し時間はbenchmarkの`wallMs`。
入力保護として各資源最大100件、区間最大1,000件/配列、作業最大20件。製品規模の確定ではない。

## 作業仮定・未決事項

1農場、最大7日、30分、分割不可、1人・農機0/1台、必須期限、makespan最小化は検証用の暫定仕様。
SC-001の3時間の計画窓も受け付ける（SRSの「1〜7日」の下限は製品レビューに残す）。
時刻はUTC ISO文字列、表示基準はAsia/Tokyo。durationは分ではなく30分スロット数。
利用可能時間は単一の登録区間に全作業を含める。隣接する別区間を自動結合しない。
先行関係は試験機能。農機種類は要求条件なので、未登録の種類も入力でき、計算でINFEASIBLEになる。
OQ-001〜014は未解決のまま。移動・休憩・資格・農学上の判断は追加しない。

## 代替案と影響

- JavaScriptを維持: 差分は小さいが型による契約の検査が弱い。
- 貪欲法のみ: 高速化できる一方、解なし・最適性の証明ができない。
- Python/OR-Tools: 将来の比較候補。今回は既存Node実装とWindows再現性を優先し、別ランタイムを追加しない。
- 今後はworker threadでUI/APIを塞がない実行、下界による枝刈り、代替ソルバーとの比較を別Issueで検証する。
