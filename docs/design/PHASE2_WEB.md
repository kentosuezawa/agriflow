## コンポーネントと処理の境界

- UI: resource editor / operation form / result summary / timeline / diff table / history。
- Application: 入力検証、入力revision管理、候補作成、承認、差分計算。
- Scheduler: 今回の型付きモデル・探索・独立検査。保存や画面へ依存しない。
- Repository: 入力・候補・確定履歴を保存。現在のJSON形式の互換性を維持する移行計画が必要。
- Solver worker（次期案）: main threadとメッセージで入力・上限・結果を受け渡し、タイムアウト/異常終了を別扱いにする。

## データと版管理

既存の`revision`、`proposal.baseRevision`、`proposal.baseVersion`、`committed.version`を継承する。
候補には入力スナップショット、期間、計算結果、作成日時を保持する。
次期案では上限値・アルゴリズム版も保持して再現性を高める。
再計画は最新入力から新しい候補を生成し、元の確定版を変更しない。
承認時に入力revisionと最新確定versionを比較し、候補を再検査してから新しい確定版として保存する。
候補の作業IDをキーに追加/削除/移動/資源変更を比較する。履歴は追記し、過去版を上書きしない。

## API契約の設計

既存の`GET /api/state`、`POST /api/entities`、`POST /api/proposals`、`POST /api/commit`をまず維持する。
新規設計では入力400、版競合409、計算内部障害500を区別し、内部情報を返さないエラー形式`{code,message,field?}`を採用する案。
これは現行APIの実装済み仕様ではない。
非同期化は別のjobs APIを追加するか互換レイヤーを置く案をレビューし、既存クライアントを無断で破壊しない。
OPTIMAL/FEASIBLEの候補だけ承認可能。UNKNOWNを解なし表示しない。INFEASIBLEは矛盾箇所の特定まで保証しない。
入力エラーと計算例外は計算4状態とは別にエラー表示する。
