# AgriFlow 最初の提出可能版 — 完成基準と /goal 指示

更新: 2026-11-09
状態: 開発目標案。要件v1.0承認ではない。以下の試作品を作るための指示は、ユーザーが /goal を開始した時点の依頼範囲として扱う。

## 1. 到達点

採用担当者や技術面接官に、GitHub・README・画面・実演で説明できる農作業計画Webアプリを作る。
DBとDockerの導入に加え、「条件を変えると計画が変わり、承認前は旧版を保ち、承認後は履歴として残る」ことを実証する。
ローカルで再現可能な完成版を最初の提出物とする。公開URL・本番運用・実農場での有用性の証明は今回の完了条件に含めない。

## 2. 想定デモと未決事項

想定する説明用の場面は、模擬農場の担当者が作業員の欠勤で計画を組み直すこと。実農場から得た事実ではない。
正常計画、欠勤による再計画、条件不足で解なし/打ち切りとなる場合を示す。

ユーザーは既存の前提を変更したいと回答しているが、変更内容は未提示。
既存の1農場・30分・最大7日・分割なし・1人/農機0〜1台・期限必須・makespanは「現行エンジンが表現できる範囲」であり、継続承認済みの製品要件ではない。
最初の提出物のデモはその既存対応範囲で構成する案とし、期間延長、共同作業、期限超過許容、目的関数変更等を勝手に追加・確定しない。
変更内容が届いた場合は要件・データモデル・テストへの影響を記録して反映し、競合する作業だけ判断を求める。
製品要件の変更希望はOPEN_QUESTIONSに残し、未解決でも何が実演可能かを明示する。

## 3. 完成判定

以下は新しい製品要件IDではなく、提出版の受入ID（PF-）である。既存FR/NFRとの対応をTRACEABILITYへ追記する。

| ID | 完成条件 | 検証と証拠 |
|---|---|---|
| PF-01 | READMEの手順でクリーンな検証環境からアプリとDBを起動できる | 必要バージョン・環境変数・起動/終了/初期化手順。実行OS/Node/Docker/Composeとコマンド・結果を記録 |
| PF-02 | 模擬データの投入・初期化ができ、初回表示で試す手順が分かる | 明示的seedコマンド。初期化はデモ用と分かる名称・確認を設け、実データを勝手に消さない |
| PF-03 | 農場・圃場・作業員・農機・作業・利用可能/不可時間を管理できる | 既存FR-001〜008の保存/再表示と異常入力。複数先行条件が編集で消えないブラウザ回帰試験 |
| PF-04 | 候補計画をタイムラインと一覧で確認できる | 日時/JST・担当者・農機・圃場・計算状態を表示。色以外でも識別できる |
| PF-05 | 欠勤→再計画→差分→明示承認→旧版参照を実演できる | SC-004をAPI/ブラウザで確認。追加/削除/時刻/担当/農機変更、承認前不変、古い候補拒否 |
| PF-06 | 計算状態とエラーを誤表示しない | OPTIMAL/FEASIBLE/INFEASIBLE/UNKNOWN、入力不正、内部失敗を区別。内部パス/スタック/秘密を画面やAPIに返さない |
| PF-07 | DBに基礎情報・候補snapshot・確定版・履歴を保存し、承認は原子的に処理する | PK/FK/制約・migration・transactionを試験。二重承認/競合/保存失敗で一部だけ更新されない |
| PF-08 | データ移行・再起動・復元で計画履歴を保つ | 元JSONを保持するimport、件数と入力/計画の同値確認、失敗時rollback、DB backup/restore、コンテナ再作成後の参照 |
| PF-09 | PC幅とスマホ幅で主要操作ができる | 例: 1440px/390pxでデモフロー。タイムラインは意図した領域内スクロール可。フォーム・ボタンにラベル、キーボード操作、空/処理中/エラー状態を確認 |
| PF-10 | 計算・API・DB・少数のブラウザ受入をCIで検証する | 固定依存。既存テストの意図を保持し、要件→test名→対象SHA→CI URLを記録。実行できないチェックを成功扱いしない |
| PF-11 | 計算性能と限界を説明できる | 小規模既知解と独立検査。現行20作業負荷を5回測り時間・状態・ノード・メモリ・計算中API応答を記録。測定環境と生値を残し、未証明の最適性や2秒保証を主張しない |
| PF-12 | 第三者が作品と技術判断を理解できる | README、実画面スクリーンショット、5分程度の実演台本、構成説明、ER図、API契約、ADR、既知制限、テスト結果、次の改善点 |
| PF-13 | GitHubから次の開発を再開できる | 小さなIssue/PR、base/head/依存、AGENTS・HANDOFF更新。未検証/未承認と次の作業が特定できる |

PF-09は実スマホでの検証済みを意味しない。Cloudのブラウザ幅による検証と区別する。
PF-11に合格性能値はまだない。基準環境と実測を示し、操作が計算で停止する場合はworker等で改善し、その前後を記録する。
画面は既存ブランドを踏まえ、余白・文字・色・ボタン・エラー表示を統一する。模擬データであることと計算の限界を明示する。

## 4. 技術と費用

- Node.js/TypeScriptと既存エンジンを活用する。全面再実装は避ける。
- DB第一候補はローカルPostgreSQL。SQL・参照制約・transaction・migration・バックアップ・サービス分離を実証する目的がある。SQLiteは単一利用者で運用が軽い代替案としてADRで比較する。両方の実装は求めない。
- Docker ComposeでappとDBを再現する案。アプリは非root、DBは内部ネットワーク、ホスト側公開はloopbackに限定。コンテナ内bindとHost/Origin検証の変更理由・防御境界をADR/試験に残す。
- 初期版はローカル単一利用者・模擬データ。公開用の認証・認可が実装済みであるとは扱わない。公開前に別のセキュリティレビューを必要とする。
- React/Next.js、別言語API、OR-Tools、外部認証、クラウドは採用理由が今回の完成条件に必要な場合のみ比較提案する。学習領域を増やすだけの目的で追加しない。
- 外部サービスの月額利用料0円、有料API/課金リソースなし。Dockerを含む利用ツールのライセンスと利用条件を確認し、有料契約を必要としない検証手順を用意する。
- 実データ/秘密はGitへ入れない。新規環境の値はサンプルと実値を分ける。GitHub Actionsも利用枠を確認し、有料枠を追加しない。

## 5. 実施順と終了地点

1. mainとPR #2/#3/#4の最新状態を再確認。古いSHAだけで判断しない。既存PoC・文書を継承。
2. PF受入表とIssueを作り、先行条件消失の修正と既存テストを確保。
3. DB/移行/ComposeのADR・ER・API契約を作り、縦に一連の業務フローを実装して試験。
4. 画面・タイムライン・差分・エラーを整え、統合/E2E/再起動・復元を確認。
5. 性能計測、README、スクリーンショット、実演台本、引き継ぎを仕上げる。
6. GitHubにPRと証拠を揃えて提出。依存PRがある場合は順序を明記する。

DB・Composeを追加しただけ、設計文書だけ、テスト未実行、P0データ保全不具合が残る状態では「完成」としない。
環境制約や承認待ちで一部が止まる場合は、独立した作業を進め、最後に未達条件と原因を明示する。
mainへのマージ・本番デプロイ・既存PRのclose・要件v1.0の承認は行わず、レビュー可能な成果物を揃えたところを終了地点とする。
