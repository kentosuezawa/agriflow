# AgriFlow — Software Requirements Specification (SRS)

**Version:** 0.1-draft / 2026-10-29  
**Status:** レビュー前。要求工学の考え方として ISO/IEC/IEEE 29148:2018 を参照。ただし規格への完全準拠は表明しない。

## 1. 目的と対象範囲
AgriFlowのMVPは、**単一農場**の限られた資源・時間による農作業スケジュールを立案し、変更時に再計算し、利用者の承認によって確定するシステムである。実農場での有効性は未検証。現段階ではテスト・学習・ポートフォリオが用途。

## 2. 定義
- **圃場 (Field):** 作業対象となる区画。境界形状・GISはMVP対象外。
- **作業 (Operation):** 圃場・所要時間・最早開始・最遅終了を持つ分割不可の単位。
- **作業員 (Worker):** 1つの作業を同時に1件だけ担当する資源。
- **農機 (Machine):** 必要な作業に1台割り当てる資源。不要なら割り当てない。
- **利用可能時間 (Availability):** 作業員・農機が稼働できる半開区間 `[start, end)`。
- **候補計画 (Schedule proposal):** 最適化計算の結果。利用者の承認がない限り確定計画を変更しない。
- **確定計画 (Committed schedule):** 利用者が明示的に承認した保存済みの版。
- **時間スロット:** 初期の仮定は30分で、計算時刻は整数スロットで表す。時間帯の基準はAsia/Tokyo。

## 3. システム境界・主要前提
- 単一農場の計画担当者が利用する。多人数同時編集はMVP対象外。
- 初期作業に必要な作業員は1名、農機は0または1台。スキルや運搬・移動時間は扱わない。
- 各作業の所要時間は入力値であり、システムによる予測はしない。
- 原則、各作業は1つの利用可能な時間区間で中断せずに完了する。
- 期間は1〜7日、時刻は時間スロット境界に整列させる（**設計仮定であり要レビュー**）。
- 圃場に対して手動設定する作業不可時間を扱う。作物・農薬・気象の専門的な安全判断は行わない。
- 非公開情報は公開デモに含めない。

## 4. 機能要件
| ID | 要件（MVP候補） | 優先度 | 主要な受け入れ条件 |
|---|---|---|---|
| **FR-001** | 単一農場の名称を登録・更新できる | Must | 作成・更新・再表示で値が一致する |
| **FR-002** | 圃場を作成・更新・一覧できる | Must | 農場内で登録し識別できる |
| **FR-003** | 作業員を登録・変更・一覧できる | Must | 名前/識別子が保存・表示される |
| **FR-004** | 農機の種類と識別子を登録・変更・一覧できる | Must | 同種複数台を区別できる |
| **FR-005** | 作業の圃場、所要時間、最早開始、最遅終了、必要農機種類を指定できる | Must | 必須項目の欠落・不正な日付・負の所要時間は拒否される |
| **FR-006** | 作業員・農機の稼働可能区間を設定できる | Must | 指定区間外には割当されない |
| **FR-007** | 圃場ごとの作業不可区間を設定できる | Must | 指定区間と重なる作業を候補に含めない |
| **FR-008** | 作業の先行関係を任意に指定できる | Should | 先行作業が完了する前に後続作業を開始しない。循環は入力拒否 |
| **FR-009** | 計算対象期間・登録データのスナップショットから候補計画を生成できる | Must | 同一条件で再実行可能な入力が記録される |
| **FR-010** | 同一作業員・農機・圃場の利用区間の重複を禁止する | Must | 競合を含む試験データで割当重複が0件 |
| **FR-011** | 各作業の必要資源と最早開始・最遅終了を守る | Must | 割り当てた各作業は時間・機械種類・資源数の要件を満たす |
| **FR-012** | 必須制約を満たす候補の中で、全作業の最終完了時刻を最小にする方向で探索する | Must | 小規模な既知最適解ケースで最適値を再現する。計算上限時は最適保証をしない |
| **FR-013** | 結果を `OPTIMAL` / `FEASIBLE` / `INFEASIBLE` / `UNKNOWN` / `ERROR` 等に区別して表示する | Must | 実行可能解なしと計算打ち切りを同一視しない |
| **FR-014** | 候補計画を作業別タイムラインと一覧で確認できる | Must | 各割当の日時・作業員・農機・圃場を閲覧できる |
| **FR-015** | 条件を変更して再計画し、旧計画との差分を確認できる | Must | 変更/削除/移動された割当を識別できる |
| **FR-016** | ユーザーが明示的に承認した候補だけを確定版にする | Must | 未承認の再計算では確定版が変更されない |
| **FR-017** | 確定計画・条件・版番号・確定日時を保存・参照できる | Must | 再起動後に履歴から計画を再表示できる |
| **FR-018** | 不正入力・実行不可・計算失敗を利用者に説明する | Must | 無効な入力と未解決状態をメッセージで区別できる |

`Should`は初期MVPへの採用をレビューで決定する要件。Mustと異なり確定ではない。

## 5. 主要な必須制約（MVP候補）
- **HC-001:** 各作業は候補内でちょうど1回割り当てられる。すべて必須作業として扱う。
- **HC-002:** 作業開始 >= 最早開始、作業終了 <= 最遅終了。
- **HC-003:** 作業は整数スロットを連続占有し、中断・分割しない。
- **HC-004:** 同一作業員・同一農機・同一圃場に重複する割当を置かない。
- **HC-005:** 作業員と農機の割当は、それぞれの稼働可能時間に完全に含まれる。
- **HC-006:** 農機を必要とする作業には要求種類に一致する農機を1台割り当てる。
- **HC-007:** 作業は圃場の作業不可区間に重ならない。
- **HC-008 (FR-008採用時):** `A -> B` なら `end(A) <= start(B)`。

**目的関数（候補）:** `minimize max(end_time(operation))` 。実際の最終成果が時間だけで測れない点、優先順位・移動時間を無視する点を明示し、利用者検証で見直す。

## 6. 非機能要件（実装前の測定目標）
| ID | 要件 | 提案する検証方法・対象 |
|---|---|---|
| **NFR-001** | ローカルで無償の開発環境を再現できる | READMEの手順で別のクリーン環境に起動でき、ライセンス費用・月額契約が不要 |
| **NFR-002** | データ整合性を維持する | 作業員/農機/圃場の無効参照を拒否。承認操作は原子的に完了する |
| **NFR-003** | 監査可能な計画履歴を保持する | 確定版の入力と結果、確定日時を記録し、後続の再計算によって旧版を変更しない |
| **NFR-004** | 正しい計算状態を表示する | 最適性未証明・解なし・計算失敗を区別するテストを用意 |
| **NFR-005** | APIの入力を検証し、内部エラー内容を無制限に公開しない | 異常な型・範囲の入力の失敗例を自動試験 |
| **NFR-006** | 公開環境の書込を保護する | 認証がない場合は公開デモを読み取り専用とし、公開環境への無許可書込ができないことを確認 |
| **NFR-007** | 主要な処理に自動テストを用意する | 制約の不変条件、APIのバリデーション、保存、承認、差分表示のテストをCIで実行 |
| **NFR-008** | 計算処理に上限を設定する | 実行時間上限を設定し、途中打ち切りと解なしを区別。上限値は技術検証後に確定 |
| **NFR-009** | パフォーマンスを定量評価する | 20作業/5圃場/3人/2台/7日を模擬し、計算時間・メモリ・API遅延を測定して記録。合格閾値はPoC後に決定 |
| **NFR-010** | 月額の外部サービス利用費を原則0円とする | 利用サービスの料金・上限・有料化時の停止手順をレビュー。無料枠超過時は機能制限を許容 |
| **NFR-011** | 秘密情報・実データをGit履歴に残さない | シークレット管理、デモデータの検査、コミット対象のレビュー |
| **NFR-012** | 再現可能な成果物を提供する | README、模擬データ、テスト実行手順、バージョン・変更履歴を公開 |

**注意:** NFR-009の数値は初期テスト規模の**仮定**であり、達成性能・保証値を示さない。

## 7. 外部インターフェース（論理要件）
- ブラウザから基礎情報登録、作業登録、計画生成、比較、承認ができる。
- APIがある場合、無効な入力を明確なエラーとして返し、計画計算の入力と結果を関連付ける。
- 初期MVPでは外部気象APIなしで計算・テストができる。連携は将来のオプション。
- 技術スタック、RESTパス、DB製品、インフラ事業者は**要件ではなく基本設計・ADRで決定**する。

## 8. データ上の制約と整合性
- スロットは半開区間 `[start, end)` とする。隣接する作業の終端と始端が同時刻なら重複とはみなさない。
- 各候補計画は作成時の入力スナップショットを参照し、再計算中に入力データが変化しても過去の結果を改ざんしない。
- 承認時には、元のデータ/確定版からの変更競合がないか検査する（ローカル単一利用者でも整合性検査は実施）。
- 日付・時刻の永続化方式（UTC/タイムゾーン）は設計フェーズで確定する。表示は日本時間を初期要件とする。

## 9. 禁止事項・対象外の安全要求
- 作業計画を「農学的・法的に安全」「利益最大」と保証しない。
- 農薬使用・機械安全・労働安全について、専門知識と法令の確認なしに実行指示を自動生成しない。
- 商用の有料外部API、実農場の未許諾データ利用はしない。
