# 5分の実演台本

前提: READMEのCompose起動と空DBへのseedを済ませる。すべて模擬データ。2026-11-02 09:00〜17:00 JST。

1. **0:00〜0:40 課題と境界** — 人・農機・圃場の二重割当を避け、欠勤時の変更を承認前に比較する試作品。現場価値・安全性は未検証。農場/資源/4作業を画面で見せる。
2. **0:40〜1:30 計画生成** — 「計画と比較」で候補を生成。OPTIMALの意味、タイムラインと一覧、トラクター1台の排他を説明。「この候補を承認して確定」でv1。
3. **1:30〜2:40 欠勤** — 基礎データで担当Aを編集。稼働時間を空欄にして保存（稼働なし）。古い候補を承認できないことを見せ、再生成。担当と時間の差分を確認。ここではv1が最新のまま。
4. **2:40〜3:20 承認と履歴** — 新候補を承認してv2。履歴でv1とv2、当時の条件を開く。リロードしても保持。計算時snapshotと版ロック/transactionの役割を説明。
5. **3:20〜4:10 例外と限界** — 必要なら担当Bも稼働なしにしてINFEASIBLEを表示（v2は不変）。UNKNOWN/FEASIBLEの意味はREADMEの状態表とテストで説明し、毎回同じ打切り状態になるとは言わない。
6. **4:10〜5:00 技術の証拠** — GitHubのCI・ER図・ADR・性能測定を開く。branch-and-boundと独立検査、PostgreSQLのFK/原子的承認、worker、Docker volume、移行/復元を簡潔に説明。未承認要件・未実施の現場調査・次の改善を示す。

スマホ幅ではタイムライン/一覧の領域を横スクロールする。実スマホ検証済みとは説明しない。
状態を戻す場合は担当者の稼働時間を元に戻す。履歴を消してやり直す代わりに別の空DB/Composeプロジェクトでseedする。seedは非空DBを上書きしない。

技術面接で説明すること: なぜ全面再実装しなかったか、SQLiteとの比較、独立検査の共通入力検証という限界、FEASIBLEが最適を意味しない理由、履歴と現行データを分けた理由、同期探索からworkerへの変更、無料と運用可能性の違い。
